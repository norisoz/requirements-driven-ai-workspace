# stakeholder-elicitation

対象工程: P02, P03

## 実行手順

1. 現在工程・成果物・出典・ユーザー確認結果を読み、実際に参照したもののみ使用する。

2. 入力済みの確認済み事項と、PROPOSED/UNKNOWN/CONFLICTEDを分離する。

3. 条件付き項目の真偽がunknownなら、その条件確認を最優先する。

4. 不足と重大問題を整理し、ユーザーには優先度の高い1〜3問を聞く。

5. ファイルを作成・変更する前に、`AGENTS.md` の最優先ルールに従い7項目の作業計画を提示し、人間の作業実行承認を得る。承認後、回答を出典付きでJSON正本に反映し、`scripts/render_markdown.py` でMarkdown版を自動生成・整合検証する。

6. 完了判定: テーラリング規則（T01〜T08）適合、必須確認済み、条件解消、重大問題・未解決情報不足なし、根拠整合、JSON↔MD整合、利用可能チャネルによる実際の人間承認。未実施の機械検証を実施済みと呼ばない。

7. 承認済み版は上書きせず、新版（`supersedes_version` 付き）と差分を作成する。

## 工程別の確認観点

### P02 ステークホルダー特定

目的: 関係者の状況と責任を整理し、未合意点を明示する。想像上の関係者の合意は認めない。

確認項目（R=必須, C=条件付き, O=任意）:

- **R** `stakeholders`：利用者、影響を受ける人、実務担当、審査担当は誰ですか。

- **R** `roles`：各関係者の役割は何ですか。

- **R** `decision_owner`：目的と最終成果物の決裁者は誰ですか。

- **R** `constraints`：関係者ごとの制約と懸念は何ですか。

- **R** `context_alignment`：現時点で共有された方向性・対立点は何ですか。

- **C** `ai_reviewers` / 条件: `uses_ai=true`：AIの出力を確認する人と、事故時に対応する人は誰ですか。

- **C** `data_controller` / 条件: `handles_sensitive_data=true`：機密・個人情報の管理責任者は誰ですか。

出力: `AGENTS.md` の「期待する毎ターンの応答（ユーザー向け表示規約）」に従い、内部変数名・スクリプト名・挨拶・否定前置きを省いた端正なビジネス表現で、現在工程・充足している情報（表）・不足している情報（表）・最優先の質問（最大3件、可能なら `ask_question` 等の選択式UI）を提示する。内容確認・承認依頼時はJSONを読ませず成果物内容を表形式で提示し、検証結果も「〜についての確認（指摘○件）」の日本語表で示す。

### P03 要求獲得

目的: 要望と要求候補を混同せず、出典のある候補を収集する。採用決定はしない。

確認項目（R=必須, C=条件付き, O=任意）:

- **R** `sources`：参照する資料、議事録、規程、ログ、関係者の意見の一覧を示してください。

- **R** `candidate_requirements`：実現したいことを関係者の言葉や資料から抽出してください。

- **R** `source_mapping`：各要求候補はどの資料や発言から導かれましたか。

- **R** `human_review_status`：抽出した要求候補を誰が確認しましたか。

- **R** `unreviewed_gaps`：未確認の情報源・関係者を列挙してください。無ければ「なし」と記録します。

- **C** `external_requirements` / 条件: `has_external_obligations=true`：関連する外部要件と条項、適用理由を示してください。

- **O** `log_analysis`：問い合わせやインシデントのログから確認すべき事項はありますか。

- **O** `minority_signals`：多数意見以外に、少数だが重要な兆候・例外・新たなニーズ（「光る原石」）はありますか。（ハンドブック8.2節 表28）

### ハンドブック準拠の確認観点（P02〜P03）
- **5W1Hの網羅確認（2.2節 表5）**: When（いつ）、Where（どこで）、Who（誰が）、What（何を）、Why（なぜ・どの価値か）、How（どう実現・どの制約か）。
- **マスの意見と「光る原石」の区別（8.2節 表28）**: AIで多数意見を集計しつつ、全体の1%未満でも重大リスク・制度変更・新ニーズにつながる少数意見（「光る原石」）を専門家と深掘りする。
- **潜在要求を見つける問い（8.3節）**: なぜそれを求めているか／本当に必要なのはその手段か別の価値か／現在の制度・業務を前提にしすぎていないか／AIが一般的回答に寄りすぎていないかを確認する。
- **要望と要求候補の分離・台帳登録（1.2節・2.6節・16.1節）**: 要望（`NEED`）と要求候補（`REQUIREMENT`）を区別し、要求管理台帳（`requirements/ledger.json`）を正本としてID管理する。
- **外部要件の社内要件変換（12.2〜12.3節 表44〜45）**: 「法令を遵守すること」等の抽象表現にとどめず、義務・禁止・条件・記録・説明責任・評価・変更へ展開する。
- **社内ルールの階層整理（13.2節 表46〜48）**: 社内規則（義務・禁止・権限）→ガイドライン（判断基準）→マニュアル（業務プロセス・例外処理）→チェックリスト（評価・監査）→FAQ/教育資料/テンプレートの階層を区別する。

出力: `AGENTS.md` の「期待する毎ターンの応答（ユーザー向け表示規約）」に従い、内部変数名・スクリプト名・挨拶・否定前置きを省いた端正なビジネス表現で、現在工程・充足している情報（表）・不足している情報（表）・最優先の質問（最大3件、可能なら `ask_question` 等の選択式UI）を提示する。内容確認・承認依頼時はJSONを読ませず成果物内容を表形式で提示し、検証結果も「〜についての確認（指摘○件）」の日本語表で示す。

## 出典との関係

工程名称と観点はIPAハンドブック第7章7.2、第6章、第16章を参照。フィールド名、分岐、ゲートは独自設計でありIPAが指定した機械規格ではない。

## 禁止事項

資料未参照の根拠を捏造しない。関係者の実際の合意・承認を代替しない。勝手に既存のベースラインを変更しない。

## 実行補足（ワークスペースルート基準）
参照ファイル: `shared/phase_definitions.json`、`shared/tailoring_profiles.json`、`shared/schemas/phases/Pxx.schema.json`。
- **`SCRIPT_VERIFIED` モード**（Python実行可能時）：`python3 scripts/resolve_tailoring.py ...`、`python3 scripts/render_markdown.py --render --verify ...`、`python3 scripts/validate_gate.py --markdown ...`（環境により `python`）で機械検証し、誤りがあれば戻す。
- **`STANDARD_SHELL_AUDIT` モード**（プログラム実行不可の社内PC）：`scripts/*.py` のロジックと `shared/*.json` を参照して全項目をチェックリスト検証し、ハッシュ・参照ID・差分はOS標準コマンド（macOS: `shasum`/`grep`/`diff`、Windows: `certutil`/`findstr`/`fc`）で実測したうえで人間レビューへ回す（機械実行済みと偽装しない）。
永続保存は差分を提示し、承認済みファイルを上書きしない。
