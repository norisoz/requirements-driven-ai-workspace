# mission-intake

対象工程: P01

## 実行手順

1. 現在工程・成果物・出典・ユーザー確認結果を読み、実際に参照したもののみ使用する。

2. 入力済みの確認済み事項と、PROPOSED/UNKNOWN/CONFLICTEDを分離する。

3. **第1段階（初回ターン最優先）：最終成果物の仕様確認** — 内容・詳細要件の質問に移る前に、以下3点を未確定のまま進めず、選択式UI（`ask_question` 等）を用いて最優先で確認・確定する（依頼文で明示済みの項目は仮案として確認のみとする）。
   - **成果物の種類**: スライド／スライドの骨子／提案書／仕様書／設計書／社内通知文書／規程・方針書／調査レポート 等
   - **出力ファイル形式**: `md`, `txt`, `docx`（Word）, `pptx`（PowerPoint）, `xlsx`（Excel）, `pdf` 等
   - **成果物の厳密さ（想定レビュー段階）**: 叩き台／上長レビュー用／他部レビュー用／最終成果物

4. **第2段階：前提・内容の確認** — 成果物仕様が確定した後、リスク分類、条件付き項目の真偽（`unknown` なら最優先）、および P01 の不足・重大問題を整理し、ユーザーには優先度の高い1〜3問を聞く。

5. ファイルを作成・変更する前に、`AGENTS.md` の最優先ルールに従い7項目の作業計画を提示し、人間の作業実行承認を得る。承認後、回答を出典付きでJSON正本に反映し、`scripts/render_markdown.py` でMarkdown版を自動生成・整合検証する。

6. 完了判定: テーラリング規則（T01〜T08）適合、必須確認済み、条件解消、重大問題・未解決情報不足なし、根拠整合、JSON↔MD整合、利用可能チャネルによる実際の人間承認。未実施の機械検証を実施済みと呼ばない。

7. 承認済み版は上書きせず、新版（`supersedes_version` 付き）と差分を作成する。

## 工程別の確認観点

### P01 目的・ミッション確認

目的: 目的と手段を区別し、成功条件を確認した暫定ミッションを作る。後工程で改訂できる。

確認項目（R=必須, C=条件付き, O=任意）:

- **R** `objective`：最終的に何を実現したいですか。手段ではなく到達状態を教えてください。

- **R** `problem`：現在、誰にどのような問題が生じていますか。

- **R** `target_value`：改善によって誰にどんな価値が生まれますか。

- **R** `beneficiaries`：利益を受ける人や組織は誰ですか。

- **R** `scope`：対象の組織、業務、適用範囲はどこまでですか。

- **R** `success_criteria`：何を確認できれば成功と判断しますか。

- **R** `risks`：実現にあたり避けたい重大なリスクは何ですか。

- **C** `quantitative_metrics` / 条件: `requires_quantitative_evaluation=true`：定量評価が必要です。指標、測定方法、目標値を示してください。

- **C** `regulatory_constraints` / 条件: `has_external_obligations=true`：対象となる法令、標準、契約上の制約は何ですか。

- **O** `out_of_scope`：今回は対象外にする業務はありますか。

- **O** `simplification_review`：所与の条件（既存業務手順・承認・帳票・社内規則）のうち、目的に照らして不要・簡素化できるものはありますか。（ハンドブック1.4節）

### ハンドブック準拠の確認観点（P01）
- **要望・要求・要件の区別（1.2節 表2）**: 「AIを使いたい」「自動化したい」等の表面的な手段・要望をそのまま要件にせず、背景にある目的・価値を抽出する。
- **所与の条件のシンプル化（1.4節）**: 既存業務・承認・規則・帳票を前提視せず、目的に照らして判断自体が本当に必要かを疑う。
- **デザイン思考・ミッションエンジニアリング（3.2〜3.3節）**: 利用者・現場の困りごと（課題の本質）と、組織・社会として達成すべき上位ミッション・成功尺度を明確化する。

出力: `AGENTS.md` の「期待する毎ターンの応答（ユーザー向け表示規約）」に従い、内部変数名・スクリプト名・挨拶・否定前置きを省いた端正なビジネス表現で、（初回は成果物作成までの工程表、続けて）現在工程・充足している情報（表）・不足している情報（表）・最優先の質問（最大3件、可能なら `ask_question` 等の選択式UI）を提示する。内容確認・承認依頼時はJSONを読ませず成果物内容を表形式で提示し、検証結果も「〜についての確認（指摘○件）」の日本語表で示す。

## 出典との関係

工程名称と観点はIPAハンドブック第7章7.2、第6章、第16章を参照。フィールド名、分岐、ゲートは独自設計でありIPAが指定した機械規格ではない。

## 禁止事項

資料未参照の根拠を捏造しない。関係者の実際の合意・承認を代替しない。勝手に既存のベースラインを変更しない。

## 実行補足（ワークスペースルート基準）
参照ファイル: `shared/phase_definitions.json`、`shared/tailoring_profiles.json`、`shared/schemas/phases/Pxx.schema.json`。
- **`SCRIPT_VERIFIED` モード**（Python実行可能時）：`python3 scripts/resolve_tailoring.py ...`、`python3 scripts/render_markdown.py --render --verify ...`、`python3 scripts/validate_gate.py --markdown ...`（環境により `python`）で機械検証し、誤りがあれば戻す。
- **`STANDARD_SHELL_AUDIT` モード**（プログラム実行不可の社内PC）：`scripts/*.py` のロジックと `shared/*.json` を参照して全項目をチェックリスト検証し、ハッシュ・参照ID・差分はOS標準コマンド（macOS: `shasum`/`grep`/`diff`、Windows: `certutil`/`findstr`/`fc`）で実測したうえで人間レビューへ回す（機械実行済みと偽装しない）。
永続保存は差分を提示し、承認済みファイルを上書きしない。
