# realization-lifecycle

対象工程: P09, P10, P11, P12

## 実行手順

1. 現在工程・成果物・出典・ユーザー確認結果を読み、実際に参照したもののみ使用する。

2. 入力済みの確認済み事項と、PROPOSED/UNKNOWN/CONFLICTEDを分離する。

3. 条件付き項目の真偽がunknownなら、その条件確認を最優先する。

4. 不足と重大問題を整理し、ユーザーには優先度の高い1〜3問を聞く。

5. ファイルを作成・変更する前に、`AGENTS.md` の最優先ルールに従い7項目の作業計画を提示し、人間の作業実行承認を得る。承認後、回答を出典付きでJSON正本に反映し、`scripts/render_markdown.py` でMarkdown版を自動生成・整合検証する。

6. 完了判定: テーラリング規則（T01〜T08）適合、必須確認済み、条件解消、重大問題・未解決情報不足なし、根拠整合、JSON↔MD整合、利用可能チャネルによる実際の人間承認。未実施の機械検証を実施済みと呼ばない。

7. 承認済み版は上書きせず、新版（`supersedes_version` 付き）と差分を作成する。

## 工程別の確認観点

### P09 実現手段への接続

目的: 要求を実現手段と検証計画につなぐ。実装・調達の完了と混同しない。

確認項目（R=必須, C=条件付き, O=任意）:

- **R** `requirement_realization_map`：各要求はどの施策、文書、業務、システムで実現しますか。

- **R** `implementation_owners`：各実現手段の実施責任者は誰ですか。

- **R** `deliverables`：作成・導入する具体的成果物は何ですか。

- **R** `verification_plan`：受入基準、検証責任者、証跡を示してください。

- **R** `handoff_decisions`：要求から実現部門への引き継ぎを誰が確認しましたか。

- **C** `ai_model_handoff` / 条件: `uses_ai=true`：AIモデル・データ・プロンプト・評価・更新の引継ぎを示してください。

- **C** `procurement_plan` / 条件: `has_external_vendor=true`：調達・契約に必要な要求・責任分界を示してください。

### ハンドブック準拠の確認観点（P09）
- **ビルディングブロック単位の調達・契約とSBOM（10.8〜10.9節・15.5節）**: 個別サービスのSLAに加え、サービス間連携・全体性能・障害切り分け・モデル更新・データ利用/返却削除・知的財産・ログ証跡の責任分界を明確化し、ソフトウェア部品と依存関係管理（SBOM）を考慮する。
- **Office成果物（`.pptx`/`.docx`/`.xlsx`）の構造検証**: Office形式の最終成果物を出力する場合は、発表用ノートの無断自動埋め込みを避け、16:9標準寸法（旧 `screen4x3` 属性除去・EMU端数なし）としたうえで、`scripts/verify_ooxml.py` でZIP・XML・リレーション・本体定義の整合を確認し、チャット上では「Officeファイル構造の整合確認（適合／指摘○件）」として報告する。実機開閉確認が未実施の場合はその旨を明記する。

出力: `AGENTS.md` の「期待する毎ターンの応答（ユーザー向け表示規約）」に従い、内部変数名・スクリプト名・挨拶・否定前置きを省いた端正なビジネス表現で、現在工程・充足している情報（表）・不足している情報（表）・最優先の質問（最大3件、可能なら `ask_question` 等の選択式UI）を提示する。内容確認・承認依頼時はJSONを読ませず成果物内容を表形式で提示し、検証結果も「〜についての確認（指摘○件）」の日本語表で示す。

### P10 運用・監視

目的: 初期ゲートは運用監視計画の準備完了。運用中は測定・評価を反復。

確認項目（R=必須, C=条件付き, O=任意）:

- **R** `monitoring_targets`：目的・要求と対応する監視対象は何ですか。

- **R** `metrics_and_methods`：指標、確認方法、評価周期を示してください。

- **R** `monitoring_owner`：運用監視の責任者は誰ですか。

- **R** `evidence_policy`：どの監視記録・証跡を残しますか。

- **R** `escalation_and_response`：逸脱があった場合の連絡先と対処手順は何ですか。

- **C** `ai_quality_monitoring` / 条件: `uses_ai=true`：AI品質劣化、モデル変更、停止条件の監視を示してください。

- **C** `sensitive_data_monitoring` / 条件: `handles_sensitive_data=true`：機密データや監査ログの適切性を確認してください。

- **O** `observations`：実運用で測定した結果はありますか。

- **C/O** `assurance_case`（`ENHANCED` かつ `uses_ai=true` で必須）：高リスクAI利用のアシュアランス・ケース（主張、根拠、証拠、前提条件）および運用後の見直し条件を定義してください。（ハンドブック5.6節）

- **レジリエンスと継続的アシュアランス（5.6節 表23〜24）**: 性能監視・安全性・公平性・頑健性・セキュリティ・説明責任・データ品質・モデル更新・運用体制・改善サイクルを継続監視し、更新トリガー8種（性能劣化、データ分布変化、苦情・異議申立て、インシデント、法令・標準変更、モデル更新、外部サービス変更、監査指摘）としきい値・安全モード切替条件を明確化する。

### P11 フィードバック・変更管理

目的: 初期ゲートは変更管理プロセスの完成。個別変更はイベント単位で再評価と承認。

確認項目（R=必須, C=条件付き, O=任意）:

- **R** `change_intake_process`：変更要求を誰がどこで受け付けますか。

- **R** `change_triggers`：法改正、事故、監査、業務変更、AI更新等の変更トリガーは何ですか。

- **R** `impact_analysis_process`：影響する要求・仕様・モデル・テストをどのように追跡しますか。

- **R** `change_approval_process`：変更の承認責任者と経路を示してください。

- **R** `revalidation_process`：変更後の再評価・再検証は誰が実施しますか。

- **O** `change_records`：現在処理中の個別変更はありますか。

- **C** `regulatory_change_process` / 条件: `has_external_obligations=true`：法令・規格変更の収集と判定手順を示してください。

### ハンドブック準拠の確認観点（P11）
- **DevOps型循環と変更の3レベル（11.3節・11.5節）**:
  - 目的・ゴールの変更 → P01（ビジネス/ミッション分析）へ戻って再構成
  - 要求・業務モデルの変更 → P04（要求分析）・P06（モデリング）へ戻って再整理
  - 実現手段・要件の変更 → P05（要求仕様化）へ戻って再整理
- **変更理由の3分類と不具合是正の区別（11.5節）**: 変更理由を「環境変化による変更（`ENVIRONMENT_CHANGE`）」「学習による変更（`LEARNING`）」「初期要求定義の不備の訂正（`INITIAL_DEFECT`）」に区別して台帳へ記録する。なお、要求・要件自体は妥当であり実装または運用がそれを満たしていない場合は、要求変更ではなく不具合または運用上の問題として是正する。

出力: `AGENTS.md` の「期待する毎ターンの応答（ユーザー向け表示規約）」に従い、内部変数名・スクリプト名・挨拶・否定前置きを省いた端正なビジネス表現で、現在工程・充足している情報（表）・不足している情報（表）・最優先の質問（最大3件、可能なら `ask_question` 等の選択式UI）を提示する。内容確認・承認依頼時はJSONを読ませず成果物内容を表形式で提示し、検証結果も「〜についての確認（指摘○件）」の日本語表で示す。

## 実行補足（ワークスペースルート基準）
参照ファイル: `shared/phase_definitions.json`、`shared/tailoring_profiles.json`、`shared/schemas/phases/Pxx.schema.json`。
- **`SCRIPT_VERIFIED` モード**（Python実行可能時）：`python3 scripts/resolve_tailoring.py ...`、`python3 scripts/render_markdown.py --render --verify ...`、`python3 scripts/validate_gate.py --markdown ...`（環境により `python`）で機械検証し、誤りがあれば戻す。
- **`STANDARD_SHELL_AUDIT` モード**（プログラム実行不可の社内PC）：`scripts/*.py` のロジックと `shared/*.json` を参照して全項目をチェックリスト検証し、ハッシュ・参照ID・差分はOS標準コマンド（macOS: `shasum`/`grep`/`diff`、Windows: `certutil`/`findstr`/`fc`）で実測したうえで人間レビューへ回す（機械実行済みと偽装しない）。
永続保存は差分を提示し、承認済みファイルを上書きしない。
